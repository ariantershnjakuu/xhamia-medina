## Architecture Decisions

### Monorepo (not full workspace)
The project uses a single `package.json` at root with a `server/` subfolder that has its own `package.json`. Not using pnpm workspaces to keep things simple — scripts use `pnpm --filter ./server`.

### Scraping approach
- Fetch `https://bislame.net/namazet/` (the daily prayer times page)
- Use `cheerio` to parse `th.prayerName` + `td.begins` pairs
- Convert "4:50 am" / "12:40 pm" → "04:50" / "12:40" 24h format
- The ekrani/ page is an alternative (has the same data but in the display board format)

### Parsed HTML structure (verified Apr 2026)
```html
<th class="prayerName ">Sabahu</th><td class="begins ">4:50 am</td>
<th class="prayerName ">L. e Diellit</th><td class="begins ">5:57 am</td>
<th class="prayerName ">Dreka</th><td class="begins ">12:40 pm</td>
<th class="prayerName ">Ikindia</th><td class="begins ">4:21 pm</td>
<th class="prayerName highlight">Akshami</th><td class="begins highlight">7:18 pm</td>
<th class="prayerName ">Jacia</th><td class="begins ">8:54 pm</td>
```

### Cache strategy
Simple in-memory cache keyed by date string ("YYYY-MM-DD" in Belgrade timezone). 
Refreshes automatically once per day. Falls back to stale cache on scrape failure.
Frontend shows ⚠ Cache indicator when serving stale data.

**Sabahu-lead invalidation (Apr 2026):** bislame.net doesn't always flip its
published times at exactly 00:00 — the 00:05 daily browser reload used to
poison the cache with yesterday's times for the whole day. Fix lives entirely
in `server/src/lib/prayer-cache.ts`: on each read, if the cache was scraped
*before* today's `Sabahu − 60min` threshold and the Belgrade wall clock has
*now crossed* it, we invalidate and re-scrape. Triggers exactly once per day
(the re-scraped cache is scraped *after* the threshold, so subsequent reads
stay fresh). Bootstrap floor of 04:00 Belgrade when sabahu is missing/invalid
— sabahu in Kosovo is never earlier than ~03:00, so 04:00 is always safely
before the real threshold. Works identically for the Express server and the
ephemeral Netlify function (no timers involved — it's a read-time check).
The existing 15-min frontend poll picks up the fresh data within minutes of
the server invalidating, well before fajr.

### Timezone
`Europe/Belgrade` = CET/CEST (same as Prishtina). Used everywhere via `Intl` APIs — no date libraries needed.

### Tailwind v4
Using `@tailwindcss/vite` plugin (no `tailwind.config.js`). 
Custom tokens defined with `@theme {}` in `index.css`.

### TV design
- No scrolling: strict `overflow: hidden` on html/body
- VW-based font sizes (`text-[2.5vw]`) for consistent scaling at 1920px
- `tabular-nums` for clock/countdown to prevent layout shifts
- `user-select: none` everywhere
- **TV overscan safe area**: root container gets `.tv-safe-area` class → `2.5vh` top/bottom, `1.5vw` left/right padding. Footer was being clipped on real TVs with only `1.5rem` bottom padding because TVs typically overscan ~5%. The vh/vw approach scales correctly across resolutions. Tunable via `--tv-safe-area-y/x` CSS vars.

## Auto-refresh & 24/7 TV robustness

### Refresh summary (after fixes)

| What | How often | Mechanism |
|---|---|---|
| Clock | Every 1 second | `setInterval` aligned to second boundary |
| Prayer times | Every 15 min | `setInterval` + `visibilitychange` + `online` event |
| Weather | Every 30 min | `setInterval` |
| Full page reload | Daily at 00:05 AM | `useAutoReload` → `window.location.reload()` |

### `useClock` bug (fixed)
The original code had a memory leak: the inner `setInterval(tick, 1000)` inside `setTimeout` was never returned to the effect cleanup, so it was never cleared on component unmount (or StrictMode double-invoke). Fixed by declaring `intervalId` in outer scope.

### `useAutoReload`
Schedules `window.location.reload()` at 00:05 AM every day. This:
- Clears accumulated browser memory (critical for 24/7 kiosk)
- Forces a fresh prayer time fetch for the new day
- 00:05 AM is safe — Sabahu in Kosovo is never before 03:00 AM even in midsummer

### `usePrayerTimes` improvements
- Reduced poll from 1h → 15min (catches midnight date change within 15 min)
- `visibilitychange` listener: re-fetches when tab becomes visible (TV wake from sleep)
- `window.online` listener: re-fetches as soon as network is restored
- On failure: keeps existing live data instead of degrading to mock (mock only used on first-ever failure)
- `cache: "no-store"` fetch option prevents browser from caching stale API responses

## Prayer reminder modal (Apr 2026)

<UserIntention>
Ambient reminder modal so passers-by glancing at the TV can see, with seconds precision, how long until the next prayer.
</UserIntention>

A third `PrayerModal` instance driven by `reminderPrayerKey`. Pops up for the first 2 minutes of every 10-minute window (X:00–X:02, X:10–X:12, …) showing a live HH:MM:SS countdown to `nextPrayer`. Suppressed whenever the adhan or iqamah modal is visible so we never stack two modals. Tunable via `REMINDER_WINDOW_MINUTES` in `App.tsx`. Reuses the same enter/exit animations and card chrome — seconds digit shares the `countdown-pulse` class with `CountdownBanner` for a subtle 1 Hz breath.

### Modal typography pass (Apr 2026, later)

<UserIntention>
The three modals (adhan, iqamah, reminder) had text that was too small and a weak hierarchy — hard to read from across the room and felt fussy.
</UserIntention>

Root cause: modal children used aggressive vw downscaling (Albanian translation at `1.1vw` ≈ 21px on 1080p, English at `0.95vw` ≈ 18px) and the adhan modal used a fixed `text-2xl` caption that clashed with the rest of the vw-based sizing. The actual prayer time in the reminder modal was smaller than its own "në orën" caption.

Changes:
- `PrayerModal.tsx` card: widened `72vw → 80vw`, `max-w-5xl → max-w-6xl`, trimmed padding to `px-14 py-10`, gap bumped to `7`, title nudged to `3.6vw`.
- Adhan modal: caption converted from fixed `text-2xl` to `1.05vw` uppercase tracked label; Arabic `2.2 → 2.7vw`, line-height opened to `1.9` for diacritics; Albanian `1.1 → 1.5vw` (the primary payload for a Kosovar audience); English stays italic/muted but at `1.05vw`. Albanian + English get `max-w-[62vw]`/`[58vw]` so long lines break earlier and read more like paragraphs than one giant line.
- Iqamah modal: added matching "Ajet Kur'anor" caption for hierarchy; Arabic ayah `2.4 → 3vw`; Albanian `1.15 → 1.55vw`; source line promoted to `1.05vw` uppercase.
- Reminder modal: prayer name `3 → 3.6vw`; digits `5.5 → 6vw`; per-digit labels `0.75 → 0.95vw`; and the actual prayer time (`18:45`) is now a hero element (`2.2vw` bold, tabular-nums) next to a small "Në orën" caption — previously it was a single small line where the caption dominated the time.

### Modal TV readability pass (Apr 2026, later still)

<UserIntention>
Modal text is still too small when read from across the room on the actual mosque TV — bump typography aggressively, let the modal fill more of the screen, and dignify the chrome.
</UserIntention>

Focus was TV viewing distance, not laptop-preview readability. Two decisions:
1. **Typography scale-up** — everything inside the modals went up ~1.4–1.5×. Adhan Arabic `2.7 → 3.6vw`, Albanian `1.5 → 2.1vw`, English `1.05 → 1.35vw`. Iqamah Arabic `3 → 4.2vw`, Albanian `1.55 → 2.2vw`, source `1.05 → 1.4vw`. Reminder prayer name `3.6 → 5.2vw`, digits `6 → 8.5vw`, per-digit labels `0.95 → 1.3vw`, time `2.2 → 3.2vw`, "Në orën" `1.05 → 1.45vw`. Captions promoted to `1.5vw` with wider tracking so they register as labels from across the room instead of disappearing.
2. **Chrome refinement in `PrayerModal.tsx`** — card widened `80vw max-w-6xl → 92vw max-w-none`, padding `px-14 py-10 → px-20 py-14`, radius bumped to `2.5rem`, backdrop darkened (`bg-black/15 → bg-black/25`) + stronger blur (`backdrop-blur-lg → xl`). Replaced the `🕌 {title} 🕌` emoji-bracket with a proper hierarchy: prayer icon (same Lucide set as `PrayerCard`) above the title, title at `4.4vw`, and a real ornamental divider (gradient line → center dot → gradient line) below. The icon is driven by the `activePrayerKey` already passed in — no new props needed.

Deliberately skipped (YAGNI): per-modal progress bar showing remaining modal time, circular countdown ring for the reminder modal, two-column Arabic/Albanian split. All would be nice; none are needed right now.

### Modal single-slot consolidation (Apr 2026, later still)

<UserIntention>
Make sure all three modals (adhan / iqamah / reminder) show during their own time window and never visually stack — in particular the "next prayer" reminder must not appear on top of the adhan or iqamah.
</UserIntention>

Root cause of the stacking: the three `<PrayerModal>` instances were rendered independently to the DOM. The timing guards in `App.tsx` (`activePrayerKey || iqamahActivePrayerKey → suppress reminder`, `minutesToNextScheduledModal < REMINDER_WINDOW_MINUTES → suppress reminder`) correctly prevented overlap in *scheduling*, but each modal still runs its own 420ms exit animation. During a transition (e.g. reminder's window ending as adhan time arrives, or adhan window capped at iqamah time transitioning straight into iqamah) both cards briefly co-exist in the DOM. Since all three sat at `z-50` and the reminder was last in JSX, **the reminder painted on top of the adhan/iqamah for ~420ms** — the exact artifact the user reported.

Fix: collapse to a single modal slot.
- `PrayerModal` now takes a `spec: PrayerModalSpec | null` (`{ id, prayerKey, title, content }`). It caches the last non-null spec internally so its exit animation can play out after spec becomes null, and keys the inner card by `spec.id` so transitions between different spec types (e.g. `reminder:dreka → adhan:dreka`) unmount/remount the card cleanly with a fresh entrance animation.
- `App.tsx` derives a single `modalSpec` via `useMemo` with explicit priority: **adhan > iqamah > reminder**. Only one is ever handed to the modal, so it's structurally impossible to stack two. Content is factored into `AdhanModalContent`, `IqamahModalContent`, `ReminderModalContent` helpers at the bottom of `App.tsx` (the reminder helper still receives `label/time/countdown` so it stays live every second).
- Existing scheduling guards in `App.tsx` are kept unchanged — they still prevent the reminder from even *scheduling* itself near an adhan/iqamah, which gives a calmer visual rhythm. The single-slot change is a belt-and-suspenders guarantee at the rendering layer.

Transition behavior after the change:
- `null → spec`: entrance animation (unchanged).
- `spec → null`: exit animation (unchanged, 420ms).
- `specA → specB` (both non-null, different `id`): old card is unmounted and the new one mounts with a fresh entrance animation — no overlap, no exit animation of the old card. Deliberate: the transitions where this happens (reminder → adhan, adhan → iqamah when their windows abut) read as "something higher-priority takes over", which is exactly the intent. Keeping a full exit-then-enter crossfade was considered but felt slower and offered no readability benefit on a TV across the room.

## Auto light/dark mode (Apr 2026)

<UserIntention>
Light mode should be active automatically from Lindja e Diellit (sunrise) until Akshami (sunset), and dark mode from Akshami until Lindja e Diellit — driven by the actual prayer times for the day, not a fixed clock schedule.
</UserIntention>

### How it works
- `src/index.css` defines the **light palette in `:root`** (warm stone + teal primary) and the **dark palette under `.dark`** (near-black + teal primary). Tailwind v4's `@custom-variant dark (&:is(.dark *));` already picks up the class.
- `src/hooks/useThemeMode.ts` exposes a pure `computeThemeMode(currentMinutes, prayers)` that returns `"light"` when `lindja ≤ now < akshami`, else `"dark"`. A thin `useThemeMode` hook toggles the `.dark` class on `document.documentElement` as a side-effect.
- Wired into `App.tsx` alongside the existing `currentMinutes` + `prayers` derivations — the class flips automatically at the minute boundary because `currentMinutes` re-derives every tick of `useClock`.
- Before prayer data loads we fall back to a coarse `6 ≤ hour < 20` heuristic — close enough to Kosovo's sunrise/sunset year-round to avoid a perceptible flash.
- `index.html` mirrors the same heuristic in a tiny inline script so the first paint lands on the correct palette (no FOUC). A `html.dark body { background }` rule keeps the pre-React body bg consistent with the theme.

### Light palette iteration (user feedback: first pass felt flat)
First pass used `bg=oklch(0.94 0.008 80)` (warm stone) + `card=oklch(0.985 0.004 80)` + `primary=oklch(0.50 0.115 186.4)`. User didn't like the UX. Root cause analysis:
- Bg & card were almost the same cream (ΔL ≈ 0.045) → no paper-stack depth.
- Bg chroma 0.008 read as "beige", fought the teal primary (near-complementary hues).
- Primary was too light (0.50) and desaturated (0.115) to command attention on a warm bg.
- `muted-foreground` at 0.42 was too weak; captions read faded.

Second pass (current):
- `bg=oklch(0.96 0.006 80)` — lighter, lower chroma → reads "paper" not "beige".
- `card=oklch(1 0 0)` — pure white for real elevation over bg.
- `primary=oklch(0.44 0.130 186.4)` — deeper + more saturated teal for presence on white cards.
- Neutrals (foreground, muted-fg, secondary-fg) shifted to hue 210 (slightly cool) so text reads crisp against the warm bg.
- `muted-foreground` raised to 0.38 for more readable captions.
- Added `transition: background-color 700ms ease, color 700ms ease` on `html`/`body` — fires only at Lindja/Akshami, so the palette swap reads as a soft dawn/dusk crossfade.

### Design choices (not done / deliberately omitted)
- No manual override / user toggle yet. If needed later, add a `localStorage` override read inside `computeThemeMode`.
